## Домен — дерево задач

- Сценарий агента [решено]
- Сценарий агента → Запрос пользователя → найти соответствующий узел [концепция/факт]
- Сценарий агента → Собрать контекст из узла и близлежащих узлов [концепция/факт]
- Сценарий агента → Исполнить запрос мутацией дерева [концепция/факт]
- Схема хранения [концепция/факт]
- Схема хранения → Плоский список узлов с полем parent; children не хранится — индекс [концепция/факт]
- Схема хранения → Лог JSONL мутаций — истина (ядро taosmd) [концепция/факт]
- Схема хранения → Проекция в памяти: Map⟨id,node⟩ + Map⟨parent,id[]⟩, реплей при старте [концепция/факт]
- Схема хранения → Снапшот на диске + хвост лога для восстановления [концепция/факт]
- Схема хранения → Вложенный JSON-объект дерева [отклонено] — примечание: перемещение = переписывание поддеревьев
- Схема хранения → Materialized path / depth в узле [отклонено] — примечание: денормализация, чинить при каждом move
- Альтернатива под рассмотрением: дерево в текстовом файле [концепция/факт] — примечание: файл целиком отдаётся модели → патчи → детерминированное применение
- Сборка контекста узла [концепция/факт]
- Сборка контекста узла → Предки — по parent до корня («где я нахожусь») [концепция/факт]
- Сборка контекста узла → Дети — childrenIndex [концепция/факт]
- Сборка контекста узла → Блокеры — blocks + обратный индекс [концепция/факт]
- Сборка контекста узла → Сёстры — дети родителя [концепция/факт]
- Сборка контекста узла → Рендер в markdown, не JSON; ~1–2k токенов на узел [концепция/факт]
- Сборка контекста узла → Как подцепить ветку родителей к семантически найденному узлу? [открытый вопрос] — примечание: вниз по вложенности работает, вверх — нет
- Мутации [решено]
- Мутации → Агент не пишет в хранилище — возвращает типизированную команду [концепция/факт] — примечание: move · set_status · rename · create
- Мутации → Валидатор перед логом; проверка цикла при move обязательна [концепция/факт]
- Мутации → Inbox как служебный элемент [концепция/факт]

## Цикл обучения — ядро

- Append-only лог действий — источник истины [решено]
- Append-only лог действий — источник истины → Запись = запрос + список мутаций + ответ пользователю [концепция/факт]
- Append-only лог действий — источник истины → Все документы и индексы собираются из лога детерминированной программой [концепция/факт]
- Ход одного запроса [концепция/факт]
- Ход одного запроса → Агент собирает контекст из релевантных документов [концепция/факт]
- Ход одного запроса → Выдаёт два структурированных результата: мутации и ответ [концепция/факт]
- Ход одного запроса → Детерминированный верификатор проверяет мутации по схеме [концепция/факт]
- Ход одного запроса → Ошибка возвращается агенту [концепция/факт]
- Ход одного запроса → Политики автоапрува; иначе эскалация апрува пользователю в интерфейсе [концепция/факт]
- Коррекция и урок [решено]
- Коррекция и урок → Пользователь выбирает запись лога и в диалоге добивается нужного результата [концепция/факт]
- Коррекция и урок → После явного подтверждения в лог пишется заменяющая запись [концепция/факт]
- Коррекция и урок → Из коррекции формируется урок — сразу в новую версию промпта агента [концепция/факт]
- Калибровка промптов (схема из диспетчера) [концепция/факт]
- Калибровка промптов (схема из диспетчера) → DSPy + GEPA как фреймворк; эталон = trainset, метрика с текстовой обратной связью [решено]
- Калибровка промптов (схема из диспетчера) → Ф0 smoke на golden-триггерах → отсечь негодную модель до трат [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Ф1 покомпонентная калибровка в изоляции, эталонные входы, keep-best, ≤8 итераций [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Ф2 интеграционный прогон — ловит каскадные расхождения [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Ф3 минимизация промпта при инварианте 100% match [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Ф4 фиксация биндинга, human-gate [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Роли разделены: судья оценивает, prompt-tuner правит, человек принимает [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Промпты = настраиваемые параметры системы; биндинг (агент, model_id), версии vN [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Два режима теста: recorded (фикстуры, каждый PR) и live (на изменение промптов) [концепция/факт]
- Калибровка промптов (схема из диспетчера) → Интерес: опенсорс-фреймворки автоматической оптимизации промптов [концепция/факт]

## Жизненный цикл задач и гейты

- Статусная модель [решено]
- Статусная модель → open · done→closed · archive→superseded · focus · pause [концепция/факт]
- Статусная модель → focus и pause — нативные статусы в форке (VALID_STATUSES + CHECK) [концепция/факт]
- Статусная модель → Оба исключены из ready и оба блокируют родителей [концепция/факт]
- Статусная модель → focus скрывает соседние ветки, pause скрывает свою; focus приоритетнее [концепция/факт]
- Статусная модель → Миграции нет — таблицы задач пересозданы со сбросом данных [концепция/факт]
- Статусная модель → focus/pause как A2A-тред состояния [отклонено]
- Фронтир = открытые видимые листья дерева parent-рёбер [концепция/факт]
- Пайплайн назначенной задачи [решено]
- Пайплайн назначенной задачи → Назначение агента на задачу фронтира запускает: планирование → апрув → исполнение → приёмка [концепция/факт]
- Пайплайн назначенной задачи → Декомпозиция ложится детьми назначенной задачи в общем дереве, видна во фронтире [концепция/факт]
- Пайплайн назначенной задачи → Агент берёт только назначенные ему задачи [концепция/факт]
- Пайплайн назначенной задачи → focus/pause на агентов не влияют — это вид пользователя [концепция/факт]
- Гейты [решено]
- Гейты → Гейт = задача taosmd с исполнителем = user [концепция/факт]
- Гейты → Ставятся только там, где необходим человек [концепция/факт]
- Гейты → Обязательные plan-approve и ACCEPT на каждом шаге [отклонено] — примечание: ревизия июля 2026
