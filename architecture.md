# Обучаемый агент на аппенд-онли логе

## 1. Система

**Цикл.** Запрос пользователя → агент собирает контекст: релевантные документы **и релевантные уроки** → выдаёт два структурированных результата: намерение (набор мутаций документов) и ответ пользователю → детерминированный верификатор проверяет намерение по схеме и правилам, применяет либо эскалирует апрув → ответ рендерит детерминированный интерфейс.

**Лог.** Запрос, использованный контекст, id поданных уроков и оба результата пишутся в аппенд-онли лог. Лог — единственный источник истины; все документы и индексы собираются из него программой.

**Обучение — два контура.**

- **Быстрый (в графе).** Пользователь открывает запись лога и в диалоге доводит результат до нужного. По явному подтверждению из коррекции создаётся объект `lesson`. Урок немедленно доступен ретриверу и с этого момента попадает в контекст релевантных запросов. Промпт не меняется.
- **Медленный (снаружи).** Внешний харнесс периодически перегоняет накопленные уроки в промпт пака, прогоняет регрессию на форке и выкатывает новую версию пака обычным релизом. Урок, стабильно улучшающий результат при подаче в контекст, — кандидат в промпт; остальные остаются контекстными.

**Инварианты.**
- Недетерминирован только агент. Запись, валидация и отображение — детерминированный код.
- Модель не имеет доступа к состоянию: она возвращает разобранный вывод, пишет в граф только код верификатора.
- Ничего не удаляется: коррекция — новая запись, а не правка старой.
- Промпт — код пака, версионируется гитом. Уроки — данные графа. Контуры не смешиваются.
- `result` фиксирует id уроков, бывших в контексте. Иначе не отличить «промпт сработал» от «повезло с ретривом».
- Из графа наружу идёт сырьё (коррекции, отказы, подтверждения); внутрь возвращается только релиз пака.

## 2. Реализация на Active Graph

### Соответствие примитивов

| Элемент системы | Примитив фреймворка |
|---|---|
| Лог действий как источник истины | Аппенд-онли лог событий; граф — его проекция, `Runtime.load` восстанавливает состояние реплеем |
| Документы, уроки, результаты | Объекты графа с типами и Pydantic-схемами, объявленными в паке |
| Запрос пользователя | `goal.created` |
| Агент | `@llm_behavior` — фреймворк собирает промпт, зовёт провайдера, валидирует схему вывода |
| Подача уроков в контекст | Сериализация объектов вьюхи в промпт; `view={"around":..., "depth":...}` бьёт размер и стоимость |
| Верификатор | Обычное `@behavior` (синхронный детерминированный код) |
| Эскалация апрува | `ctx.propose_object` → `approval.proposed` → `rt.pending_approvals()` → `approve/deny` |
| Автоапрув | `PackPolicy(requires_approval=[...], settings_key=...)` |
| Схемная проверка мутаций | Валидация Pydantic-схемы типа при `add_object` |
| Логирование контекста | `Runtime(trace_context_reads=True)` → `context.read` с id прочитанных объектов, включая сериализованные в промпт |
| Внешний поиск/индекс | `@tool` → `tool.requested/responded`, кэш по хешу аргументов, детерминированный реплей |
| Отказ верификатора | Событие (`patch.rejected`, кастомный `result.rejected`), не исключение |
| Версия промпта в истории | `pack.loaded` несёт версию пака и хеши промптов |
| Регрессия версии пака | `fork(at_event)` → `load_pack(candidate)` → прогон → сравнение |
| Воспроизводимость | Кэш LLM по хешу промпта; strict-replay падает на первом расхождении |

### Состав пака

**Типы объектов:** `document`, `request`, `result`, `correction`, `lesson`.
**Типы связей:** `derived_from`, `corrects`, `used_lesson`.

**Поведения:**
1. `retriever` — `@tool`, возвращает id якорных документов и релевантных уроков; дальше навигация по графу через `view`.
2. `agent` — `@llm_behavior` на `goal.created`, `correction` и `result.rejected`; кладёт один объект `result` со всем набором предполагаемых правок, ответом пользователю и id использованных уроков.
3. `verifier` — `@behavior` на `object.created / type=result`: валидирует весь набор до первой записи, сверяет версии целевых объектов, затем применяет либо эмитит `result.rejected` со структурным кодом причины.
4. `lesson_extractor` — на `approval.granted` по корректирующему результату создаёт объект `lesson`.

**Политика:** типы, требующие подтверждения пользователя, объявляются в `PackPolicy`; `settings_key` даёт автоапрув в dev и ручной апрув в проде без правки кода.

## 3. Разрыв: чего нет и как дописать

### 3.0 Политика разработки, закрывающая 3.1–3.5

**Агент пишет предложение — верификатор апрувит и применяет.** Единственный писатель в граф — верификатор; вывод модели материализуется как один объект `result` и ничего больше. Всё, что фреймворк не даёт из коробки (атомарность набора, перехват мутаций, петля возврата, семантическая гранулярность, условный автоапрув), решается этим одним правилом: до апрува граф не тронут, после апрува набор применяется целиком детерминированным кодом. Пункты ниже — детали реализации этого правила, а не самостоятельные проблемы.

Правила ревью:
- ни одно `@llm_behavior` не вызывает `add_object`/`patch_object`/`add_relation`;
- всё намерение — в одном объекте, включая наблюдённые версии целей;
- схемы и версии проверяются до первой записи;
- отказ — событие со структурным кодом причины, не исключение;
- каждая петля имеет счётчик попыток и порог эскалации.

### 3.1 Транзакция над набором мутаций
**Нет.** Каждая мутация эмитит событие немедленно; транзакции над несколькими объектами в API нет. Схемная валидация на `add_object` срабатывает в момент записи — слишком поздно для гейта.
**Решение.** Атомарная единица — намерение: агент кладёт один объект `result`, содержащий все правки и наблюдённые версии целей. Верификатор валидирует набор Pydantic-моделями напрямую **до** первой записи и сверяет версии; при полном успехе применяет правки внутри одного синхронного тела поведения.
**Если частичная запись критична.** Настоящая транзакция — форк: правки применяются в форке, `promote` коммитит атомарно, выброшенный форк = откат. Цена: только SQLite; дельта применяется тихо, реактивная логика вешается на `promote.applied`; промоут только для прямого потомка.
**Чего делать не надо.** Оптимистично применять и откатывать компенсирующими патчами: откат не отменяет уже отработавшие downstream-поведения, обратный патч сам может упереться в конфликт версий, проекция врёт в промежутке. Компенсация — только для аварии на середине уже провалидированного набора.

### 3.2 Перехват всех мутаций
**Нет.** Прямые `add_object`/`patch_object` приземляются немедленно; двухфазный путь — opt-in, выбор автора поведения.
**Решение.** Инвариант пака, проверяемый на ревью: вывод агента не пишет в граф, только объект `result`. Держится на том, что модель не имеет доступа к графу вообще.

### 3.3 Петля возврата отвергнутого результата
**Нет как вызова, есть как реакции.**
**Решение.** `verifier` эмитит `result.rejected` с кодом причины и ссылкой на запрос; `agent` подписан на это событие наряду с `goal.created`. Изменившийся промпт меняет хеш, кэш не срабатывает. Обязательно: счётчик `attempt` в объекте и порог, за которым эскалация вместо нового запроса. Причина — стабильный дискриминатор (`schema.field_missing`, `policy.needs_approval`, `version.conflict`), не проза.

### 3.4 Гранулярность подписки — объект, не поле
**Ограничение.** Подписка на `object.created` / `patch.applied`; `where=` — равенство по точечным путям. Пороги и «поле изменилось» так не выражаются. Структура payload у `patch.applied` не зафиксирована в документации — проверять через `inspect --event`.
**Решение.** Низкоуровневое поведение ловит `patch.applied`, определяет семантически значимый переход и эмитит доменное событие; остальные поведения подписаны на него. Если на одно поле подписано несколько поведений — поле должно быть отдельным объектом.

### 3.5 Условный автоапрув
**Нет.** Политика — список типов объектов плюс один булев флаг.
**Решение.** Правила по содержимому — код верификатора; политика пака остаётся для типов, требующих подтверждения безусловно.

### 3.6 Отбор уроков в контекст
**Нет.** Ранжирования, релевантности и лимитов у фреймворка нет; `view` — декларация скоупа чтения, не query-язык.
**Решение.** Отбор уроков — тот же `@tool`, что и ретрив документов. Нужны свои правила: сколько уроков подавать, как разрешать противоречия между ними, как выводить устаревшие из оборота (статус `retired`, не удаление). Это основной новый код быстрого контура и главное место деградации: неограниченно растущий набор уроков в контексте бьёт и по стоимости, и по качеству.

### 3.7 Ретрив документов
**Нет.** Ни индекса, ни полнотекста, ни векторов. Паттерны — подмножество Cypher для активации поведений, не для поиска.
**Решение.** Ретривер как `@tool`, ходящий во внешний индекс; индекс пересобирается из лога как ещё одна проекция. В v1, если документы связаны типизированными рёбрами, может хватить навигации `around` + `depth` без индекса.

### 3.8 Медленный контур обучения
**Нет полностью — и это правильно, он живёт снаружи.**
**Решение.** Внешний харнесс: читает store, отбирает уроки-кандидаты (по частоте срабатывания и влиянию на результат), пересобирает промпт пака, гоняет регрессию по документированному сценарию `fork → load_pack(candidate) → run → сравнение`, выкатывает пак релизом. Критерии приёма — обычные тесты в репозитории пака, рядом с промптом. Часть точек держать как holdout. `rt.diff` в этом цикле — инструмент расследования упавшей точки, не критерий: он структурный, семантическое сравнение объявлено задачей вызывающего.
**Почему снаружи.** `fork`/`promote` — операторские вызовы над рантаймом; тело поведения обязано быть детерминированным и не имеет права ветвить историю. Цикл обучения не может быть поведением в графе.

### 3.9 Интерфейс
**Нет намеренно.** Ни UI, ни HTTP-сервера, ни стриминга. Санкционированный шов — `EventSink`.
**Решение.** Очередь апрувов и рендер ответа — свои, поверх `pending_approvals()` и `EventSink`.

### 3.10 Замена записи
**Нет.** Лог строго append-only (`truncate_after` — операторский примитив, не для поведений).
**Решение.** См. раздел 4.

## 4. Коррекция результата

Основной путь — без форка. Применяется, когда исходный результат не породил каскада зависимых мутаций.

1. Пользователь на записи лога создаёт объект `correction` (`target_result`, комментарий).
2. `agent` подписан на `object.created / type=correction`: читает исходный `result`, его контекст и комментарий, выдаёт новый `result` со связью `corrects` на старый.
3. Диалог — та же петля, что и `result.rejected`: пользователь не согласен → новая `correction` → новый `result`.
4. Явное подтверждение принятия — это апрув: корректирующий результат идёт через `propose_object`, попадает в `pending_approvals()` и применяется только после `approve`.
5. Верификатор применяет дельту относительно **текущего** состояния, а не исходного намерения. Версии целей уже сдвинулись — сверка версий обязательна.
6. Старый `result` патчится в `superseded` и остаётся в логе.
7. `lesson_extractor` на `approval.granted` создаёт `lesson` со ссылкой на пару «было/стало». Урок сразу доступен ретриверу — это и есть быстрый контур обучения.

**Через форк** — только когда исходный результат породил downstream-мутации, требующие пересчёта: форк от события исходного `result`, подача коррекции, прогон, `diff` для обзора последствий, `promote`. Конфликт с работой родителя после точки форка валит промоут целиком; восстановление — форкнуться заново от текущей вершины и переприменить коррекцию там.

Правило выбора: каскада нет — путь без форка, каскад есть — форк.

## Ограничения, определяющие выбор

- **Хранилище — SQLite:** `fork()` требует SQLite-рантайма. Postgres — только через миграцию.
- **Контракт детерминизма:** в теле поведения запрещены `random`, `datetime.now()`, `uuid4()`, прямой I/O. Время — из события, id — из `graph.ids`, сеть — через `@tool`, LLM — через `@llm_behavior`. Статически не проверяется: нарушение всплывает позже как `replay-divergence-error`. Enforcement — эталонный strict-replay в CI.
- **Проекция под нагрузкой:** снапшотов нет, реплей линейно дорожает с длиной лога.
- **Стоимость контекста:** уроки и документы в промпте — главный драйвер цены; `view` со скоупом обязателен.
