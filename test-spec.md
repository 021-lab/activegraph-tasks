# v1 «Список задач» — тестовая спецификация

Самодостаточный тест: старт с пустой базы, все данные создаются запросами пользователя. Сроков в схеме нет — состояние задачи выражается статусом. Обучение (уроки, промпт) вне скоупа.

## 0. Схемы и правила

```python
Task     = {title, status: open|done|cancelled, project: str|None,
            priority: low|normal|high}
Result   = {request_id, answer, mutations: [Mutation], candidates: [id],
            attempt: int, state: proposed|applied|rejected|superseded}
Mutation = {op: create|patch|remove, type, target, target_version, data}
```

- **R1** не более одной мутации на объект в наборе (иначе `set.duplicate_target`);
- **R2** схемы и версии всех целей проверяются **до** первой записи и **до** гейта; ошибка любой мутации → не применяется ни одна;
- **R3** гейт апрува — чистая функция набора и связей результата: `op=remove`, изменение `status`, объём > 10, наличие связи `corrects`. Самоотчёта агента в гейте нет;
- **R4** `applier` после апрува валидирует заново: апрув не отменяет проверку версий;
- **R5** при применении корректирующего результата предки по `corrects` в состоянии `applied` → `superseded`; `rejected` остаются `rejected`;
- **R6** неоднозначность: разрыв score между 1-м и 2-м кандидатом < 0.10;
- **R7** пустой набор мутаций — нормальный результат: применяется, гейт не поднимает, состояние `applied`. Интерфейс различает по `len(mutations)`, отдельного статуса нет.

## 2. Сквозной пользовательский опыт

**Исходно: база пуста.**

| Шаг | Контекст | Пользователь | Что видит |
|---|---|---|---|
| **T1** | — | «заведи задачу: свести отчёт по прайсу» | «создал». В P1 одна карточка, статус «открыта» |
| **T2** | — | «добавь: обновить прайс поставщика и созвон с подрядчиком по прайсу» | «создал 2 задачи». В P1 три карточки |
| **T3** | — | «закрой прайс» | «под „прайс“ подходят три задачи — какую?» со списком. P5 пуста, P1 без изменений |
| **T4** | **закреплена** «обновить прайс поставщика» | «подними приоритет у этой» | «приоритет высокий». В P1 обновился приоритет |
| **T5** | — | «закрой отчёт» | «смена статуса требует подтверждения» → «применить» → «готово». Отчёт «выполнена» |
| **T6** | — | «удали созвон, он не нужен» | «удаление требует подтверждения» → «отклонить» → в P4 «отклонено». Созвон на месте |
| **T7** | — | «отчёт нельзя считать готовым, пока не прошёл созвон» | «отчёт закрыт, а созвон открыт — предлагаю вернуть отчёт в работу. Подтвердите» → «применить» → «готово». Отчёт снова «открыта» |
| **T8** | **закреплён** «свести отчёт» | «приоритет отчёта critical, а созвон закрой» | «не смог: допустимы low / normal / high». Созвон тоже остался открытым |
| **T9** | результат T7 | «поправить»: «отчёт закрыт правильно, отменить надо созвон» → затем в P2 вручную ставит отчёту высокий приоритет → в P5 «применить» | предложение в P4 (2 изменения); после «применить» — «коррекция устарела, задача изменилась». Ни отчёт, ни созвон не изменились |
| **T9.1** | результат T9 | «повтори с учётом моей правки» → «применить» | «готово». Отчёт «выполнена», созвон «отменена». Предложение T7 помечено «заменено» |
| **T10** | — | в P2 «откуда это», затем P6 | цепочку от запроса T1 до апрува T9.1; в истории все шаги, включая отклонённые и ошибочные |

## 3. Лог вызова поведений

Формат: `событие → поведение(данные) → результат`. Комментарий — почему так, а не иначе.

### T1 — пустой поиск, автоапрув

```
goal.created {text: "заведи задачу: свести отчёт по прайсу"}
→ find_context("отчёт прайс") → {tasks: []}
   # база пуста; пустой результат — не ошибка, дедупликация не нужна
→ agent(view: пусто) → r_01 {mutations: [create task {title: "свести отчёт
   по прайсу"}]}                       # status=open, priority=normal по схеме
→ verifier(r_01): R1 ок, R2 → [], R3 → False (create, объём 1)
   apply_all → t_01 v1; r_01.state = applied
context.read {objects: []}             # пустой контекст фиксируется тоже
```

### T2 — автоапрув, посев фикстуры

```
goal.created {text: "обновить прайс поставщика и созвон с подрядчиком по прайсу"}
→ find_context("прайс поставщик созвон") → {tasks: [t_01]}
→ agent(view: t_01) → r_02 {mutations: [create «обновить прайс поставщика»,
   create «созвон с подрядчиком по прайсу»]}
   # проверяем факт передачи t_01 во view; заголовки не совпадают,
   # дубля тут и не возникло бы
→ verifier: R1 ок (разные цели), R3 → False → apply_all → t_02 v1, t_03 v1
```

### T3 — неоднозначность: уточнение, не апрув

```
goal.created {text: "закрой прайс"}
→ find_context("прайс") → {tasks: [t_01 .81, t_02 .79, t_03 .77]}
→ agent → r_03 {mutations: [], candidates: [t_01,t_02,t_03],
                answer: "какую именно?"}
   # R6: разрыв .02 < .10 → выбор не делается моделью
→ verifier(r_03): R2 → [] (проверять нечего); R3 → False (набор пуст)
   apply_all → 0 записей; r_03.state = applied
   # R7: в P5 записи НЕ появляется — подтверждать пустую запись бессмысленно.
   # Интерфейс показывает вопрос, потому что mutations пуст, а candidates нет
```

### T4 — закреплённый контекст, безопасный патч

```
goal.created {text: "подними приоритет у этой", pinned: [t_02 @v1]}
→ find_context: не вызывается          # закрепление снимает неоднозначность T3
→ agent(view: t_02) → r_04 {mutations: [patch t_02 {priority: "high"},
   target_version: 1]}
→ verifier: version 1 == 1; R3 → False (не status, не remove, объём 1)
   apply_all → t_02 v2; r_04 applied
context.read {objects: [t_02]}         # событие есть, хотя tool не вызывался
```

### T5 — смена статуса: эскалация и подтверждение

```
goal.created {text: "закрой отчёт"}
→ find_context("отчёт") → {tasks: [t_01 .88, t_02 .44, t_03 .41]}
   # R6: разрыв .44 > .10 → однозначно
→ agent → r_05 {mutations: [patch t_01 {status: "done"}, target_version: 1]}
→ verifier(r_05): R2 → []; R3 → True (изменение status)
   propose_object("commit", {result: r_05})     # граф не тронут
approval.granted {by: user}
→ applier(r_05): R4 → валидация заново, version 1 == 1
   patch t_01 → v2 {status: done}; r_05 applied
```

### T6 — удаление: эскалация и отказ

```
goal.created {text: "удали созвон, он не нужен"}
→ find_context("созвон подрядчик") → {tasks: [t_03 .88, t_01 .41]}
→ agent → r_06 {mutations: [remove t_03, target_version: 1]}
→ verifier(r_06): R3 → True (op=remove) → propose_object("commit")
approval.denied {by: user}
→ on_denied → r_06.state = rejected
   # t_03 v1 без изменений; r_06 остаётся в логе
```

### T7 — противоречие данных и требования

```
goal.created {text: "отчёт нельзя считать готовым, пока не прошёл созвон"}
→ find_context("отчёт созвон готовность") → {tasks: [t_01 .82, t_03 .80]}
   # два разных якоря, каждый в своей роли → R6 к паре не применяется
→ agent(view: t_01 done, t_03 open)
   → r_07 {mutations: [patch t_01 {status: "open"}, target_version: 2],
      answer: "отчёт закрыт, созвон открыт — возвращаю отчёт в работу"}
   # требование противоречит данным; агент выбирает разрешение и объясняет его.
   # гейт поднимается не самоотчётом, а тем, что в наборе меняется status (R3)
→ verifier(r_07): R2 → []; R3 → True → propose_object("commit")
approval.granted → applier(r_07): version 2 == 2 → t_01 v3 {status: open}
   r_07.state = applied
```

### T8 — отказ по схеме, атомарность по двум объектам

```
goal.created {text: "приоритет отчёта critical, созвон закрой", pinned: [t_01 @v3]}
→ find_context("созвон") → {tasks: [t_03 .88]}     # второй якорь не закреплён
→ agent → r_08 {mutations: [patch t_01 {priority: "critical"}, target_version: 3],
                            [patch t_03 {status: "done"}, target_version: 1]}
→ verifier(r_08)
   R1 ок (разные цели)
   R2 → [Err(schema.invalid_value, t_01.priority)]      # вторая мутация валидна
   emit result.rejected {reason: "schema.invalid_value"}
   # R2 идёт до R3: гейт даже не оценивается, хотя status в наборе есть.
   # выход до первой записи → t_03 не изменён, и это видно в интерфейсе
t_01 v3, t_03 v1; attempt=1 при пороге 1 → ретрая нет
```

### T9 — коррекция, ручная правка, конфликт на апруве

```
object.created {type: correction, target_result: r_07,
                comment: "отчёт закрыт правильно, отменить надо созвон"}
→ agent(view: r_07 + t_01 + t_03 + correction)
   → r_09 {attempt: 2, mutations: [patch t_01 {status: "done"},
      target_version: 3], [patch t_03 {status: "cancelled"}, target_version: 1]}
   add_relation r_09 -corrects-> r_07
→ verifier(r_09): R2 → []; R3 → True (status и связь corrects)
   propose_object("commit", {result: r_09})

patch.applied {object: t_01, diff: {priority: high}, version: 4}
   # ручная правка пользователем через P2, пока r_09 в очереди;
   # тот же путь записи и та же валидация схемы, источник — интерфейс

approval.granted {object: commit_r_09}
→ applier(r_09): R4 → валидация заново: version t_01 = 4 ≠ 3
   emit result.rejected {reason: "version.conflict", seen: 3, actual: 4}
   r_09.state = rejected
   # апрув не бипасс: иначе коррекция затёрла бы правку пользователя.
   # t_03 тоже не изменён — набор атомарен и на этапе применения
   # r_07 остаётся applied: по R5 superseded ставится только при применении
```

### T9.1 — второй раунд

```
object.created {type: correction, target_result: r_09,
                comment: "повтори с учётом моей правки"}
→ agent(view: r_09 + t_01@v4 + t_03@v1 + correction)
   → r_10 {attempt: 3, mutations: [patch t_01 {status: "done"},
      target_version: 4], [patch t_03 {status: "cancelled"}, target_version: 1]}
   add_relation r_10 -corrects-> r_09
→ verifier(r_10): R3 → True → propose_object("commit")
approval.granted
→ applier(r_10): версии совпадают → t_01 v5 {status: done, priority: high},
   t_03 v2 {status: cancelled}; r_10 applied
→ R5 по цепочке corrects: r_09 rejected остаётся rejected; r_07 → superseded
   # состояния патчатся, объекты не удаляются
```

### T10 — аудит

```
trace.causal_chain(t_01)
→ [goal.created(T1) → llm.responded → object.created(r_01) → object.created(t_01)
   → object.created(r_05) → approval.granted → patch.applied(t_01)   # T5
   → object.created(r_07) → approval.granted → patch.applied(t_01)   # T7
   → patch.applied(t_01)                                             # T9 вручную
   → object.created(correction) → object.created(r_10)
   → approval.granted → patch.applied(t_01)]                         # T9.1
context.read: по одному событию на каждый вызов agent, включая пустое из T1
   # требует Runtime(trace_context_reads=True)
```

## 5. Исправлено в этой версии

1. **Сроки убраны** из схемы и из всех запросов: состояние выражается статусом, «перенеси на пятницу» заменено на смену статуса и приоритета.
2. **Состояние `answered` удалено.** Пустой набор мутаций — обычный успешный результат (R7); «были ли изменения» выводится из `len(mutations)`, в enum лишнему статусу места нет.
3. **`confirm_reason` удалён.** Гейт апрува вернулся к чистой функции набора (R3): самоотчёт агента о строгости давал ему канал влияния на собственную проверку. Противоречие в T7 эскалируется потому, что в наборе меняется `status`, а не потому, что агент так сказал.
4. **Зафиксирован порядок R2 → R3**: валидация до гейта. Иначе невалидный набор попадал бы в очередь подтверждений (видно в T8, где `status` в наборе есть, но гейт не оценивается).
5. **Атомарность проверяется дважды** — до записи (T8) и после апрува (T9), где вторая мутация тоже не применилась.
